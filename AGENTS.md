# Reglas del proyecto

- Code is layered per ARCHITECTURE.md (domain/application/infrastructure/service/presentation/shared); keep dependencies pointing inward — why: Clean Architecture is the thesis' structural requirement.
- `domain/` must not import React, `@/integrations/*`, `infrastructure/`, `service/` or `presentation/` — why: domain stays pure and unit-testable (enforced by ESLint).
- Use cases receive ports via a deps object; Supabase adapters live in `infrastructure/persistence/supabase` and are composed in server functions — why: dependency inversion, tests use in-memory fakes.
- Server functions only authenticate, validate with zod and delegate — why: single responsibility.
- Files carry brief Spanish comments explaining their purpose — why: thesis documentation.
- Access to other users' data is checked server-side via `has_role`; names/emails only for the psychologist role — why: privacy of pilot participants.

- Research admin operations use an injected `AdminRepository` and clock; privileged identity reads are supplied lazily by authenticated service handlers and reached only after psychologist authorization — why: preserves privacy and makes use cases testable without cloud dependencies.
- Keep `useUserStore` as a compatibility facade over presentation hooks for progress queries, profile/settings, missions and inventory; retain query keys and immediate profile cache updates — why: separates responsibilities without breaking consumers or onboarding navigation.

- Shared mission reward and attribute contracts live in domain/gamification/rewards and are re-exported by the presentation facade — why: domain consumers must not import presentation types.
- Passive check-in signals are optional model features excluded from coverage when missing — why: users without that data must not get a weaker signal.
- The admin what-if simulator calls the active model through `application/research/simulate.ts` and never persists — why: explainability must match real inference exactly.
- The active wellbeing model is `domain/wellbeing/decision.ts`, which wraps the logistic baseline with personal baseline, protective factors, academic calendar, safety rules, confidence and hysteresis; callers pass previous levels and exam period as `DecisionContext` — why: decision rules stay pure, testable and identical for students, admins and the simulator.
- Admin dashboard series are computed by the pure `domain/research/dashboard.ts` from consented data only — why: charts for both roles share one tested aggregation and never leak non-consented data.
- Dashboard, profile and AR missions share the lazy browser-only ArchetypeScene; model selection and screen bounds stay in domain/identity, while ARCompanion owns camera-relative placement — why: consistent avatars without SSR WebGL or location collection.
- In AR missions ARCompanion lets the user tap (Cheer + mission action), drag, rotate and resize the 3D character via buttons, keyboard or two-finger gestures; zoom limits and facing normalization live in domain/identity/avatarMotion, and missions pass `celebrate` when finished — why: interaction must work the same in every AR mission and stay testable.
- No emojis in the UI: game content (missions, achievements, items, archetypes, zones) carries an `icon` key rendered by `GameIcon` (game-icons.net, CC BY 3.0, credited in Perfil and CREDITS.md; regenerate `gameIconData.ts` with `scripts/build-game-icons.mjs` after adding a key), and interface chrome uses lucide — why: consistent look on every phone, medieval style, and only the used SVGs ship.
- UI motion uses the `motion` library through `MotionProvider` (LazyMotion + `m.*` only) with `PageTransition` and `Reveal`; device preferences (reduce motion, sound, haptics) live in localStorage via `shared/devicePrefs` (no DB column) and every animation, 3D scene, sound and vibration must honour them — why: per-device comfort settings without migrations, and one switch that calms the whole app.
- AR missions are themed by zone: `domain/world/missionZones.ts` assigns each AR mission type a zone (aura→valle, energy→bosque, focus→reino, walk→montana; non-AR missions still group by category) and the AR view shows the character on that zone's island (`AR_PLATFORMS`) with the zone chip and tint — why: each zone has its own AR experience with tested assignment rules.
- World zone cards share ONE WebGL canvas (`WorldThumbnailsCanvas`, drei `View` tracking each card); only the open zone detail has its own canvas. 3D models are preloaded by `ScenePreloader` when the browser is idle — why: fewer WebGL contexts on low-end phones and 3D that appears without waiting.
- World zones (valle, bosque, reino, montana) render as KayKit Medieval Hexagon dioramas from public/models/world-kit.glb; layouts, piece reveal by zone progress and hex math live in the pure `domain/world/dioramas.ts`, while lighting by season is presentation — why: the world reflects real progress with tested rules and one small shared asset.
- Archetype avatars are trimmed KayKit Adventurers models (CC0) in public/models with only Idle, Walking_A and Cheer; the clip to play is chosen by the pure `avatarAnimation` in domain/identity — why: medieval look that matches each archetype, small downloads, and testable motion rules including reduced motion.
- Mission rewards are taken server-side from the catalog in `domain/gamification/missionsData` (the client only sends missionId and duration) through `infrastructure/persistence/supabase/missionCompletion`, shared by the server function and the MCP tool — why: progress cannot be inflated from the phone and both entry points follow the same rules.
- Each archetype has mission category affinities in `domain/identity/archetype` (+20 % XP via `AFFINITY_XP_MULT`); affine missions are listed first, preferred by "Tu siguiente paso" and badged in Misiones and Comunidad — why: the chosen archetype must shape the mission experience, not only the look.
- Finishing any mission first shows the `MissionCompleteBanner` ("¡Misión cumplida!", `missionComplete` feedback event, `MISSION_BANNER_MS`); AR missions announce it via `onAchieved` and `useMissionFinale` before the avatar celebrates, and rewards, level-up and achievements are emitted by the missions screen only after the banner — why: one clear, motivating moment per mission without overlapping celebrations.
- WHO phase 1: the WHO-5 "Pergamino del bienestar" (`domain/wellbeing/who5.ts`) is asked every 14 days as the scale defines, stored in `wellbeing_scales` (code WHO5) and inverted to distress for the model (raw ≤ 7 triggers `escala_severa`); weekly physical activity follows the WHO 2020 guideline (`domain/wellbeing/activity.ts`, table `activity_logs`, vigorous minutes count double, weeks start Monday); the support protocol inspired by WHO LIVE LIFE (`domain/wellbeing/support.ts`) shows a "Pide ayuda" button in Bienestar and Perfil and a banner when the compass is in alert, a safety rule fires or WHO-5 is very low — why: health content backed by citable WHO guidance, and help is always one tap away.
- Consent is versioned (`CONSENT_VERSION`); bumping it asks every participant to accept again before any wellbeing data is recorded — why: informed consent must cover each new kind of data and its use for training models.
- WHO phase 2: "Elegidas para ti" comes from our own recommender (`domain/wellbeing/recommender.ts`, `thompson-v1`): a Beta-Bernoulli Thompson sampler per mission category and student, reward = the next check-in (≤ 2 days) improves, archetype-affine categories start with Beta(2,1), seeded by student + day so it is stable; every recommendation shown is logged in `recommendation_log` (only with consent) and marked taken when that mission is completed the same day; model versions live in `model_versions` and the research panel shows acceptance — why: a self-built, explainable ML component that can be evaluated for the thesis.
- Guided paths (`Mission.path`, `PATHS`, `pathBlocker`): the WHO "Doing What Matters" route (dwm-1…dwm-5) unlocks step by step, checked both in the UI and in `completeCatalogMission` — why: the five ACT skills of the WHO guide build on each other.
- Mission catalog quality: titles are unique, every quiz has its own question bank in `domain/gamification/quizzes.ts`, "steps" missions carry `steps` (and `source` when based on WHO guidance), meditations can carry their own guide (`MEDITATION_GUIDES`), and archetype-exclusive missions (`Mission.archetype`, 3 per archetype) are only reachable through `visibleMissions(archetype)` and rejected server-side for other archetypes; `missionsCatalog.test.ts` guards this — why: varied, non-repeated, well-written missions that each archetype can feel as its own.
- The Missions screen is organised as: Elegidas para ti → Solo para tu arquetipo → WHO route → category filter chips → sections by category (pending first, done today dimmed in place) → collapsible "Por desbloquear"; cards show estimated minutes (`estimateMinutes`), XP, rarity and affinity — why: fast scanning on a phone and a clear sense of progress per area.
- Phase 3 psychologist alerts: the pure `domain/research/alerts.ts` turns consented student rows into a prioritized queue (urgente: safety rule or WHO-5 ≤ 7; atención: model level alto or WHO-5 < 13; vigilar: moderado getting worse, ≥ 5 days without check-in, or — with no check-in in the 4-week window — ≥ 5 days since the last mission) with follow-up windows of 2/7/14 days; `/admin` shows `AlertsPanel` first and the student file shows the same alert. Admin inference receives the WHO-5 scales exactly like the student's own inference — why: the clinical team sees who needs contact first, with the same rules everywhere.
- Guilds (gremios): 3–5 students, tables `guilds`, `guild_members` (one guild per student) and `guild_chest_claims` (migration 0006); writes only through SECURITY DEFINER functions (`create_guild`, `join_guild`, `leave_guild`), members read only their own guild and `guild_roster` exposes just name, archetype and level. The weekly challenge rotates by mission category (`domain/community/guilds.ts`, AR counts as movement) and `guild_week_progress` returns only the collective total and number of contributors — never per-person counts, so there is no ranking. The chest is opened only through the atomic SECURITY DEFINER `claim_guild_chest` (migration 0007: students cannot insert claims), once per student per week, when the guild reaches 3 missions per member and the student contributed; its rotation and reward mirror the domain and `guildSql.test.ts` keeps them in sync; achievements group "gremio" — why: cooperation tied to missions without social comparison.
- Daily reminders are per device (`shared/devicePrefs`: off by default, `reminderTime`, `reminderShownOn`); rules live in `domain/wellbeing/reminders.ts`: slots 7:00–21:00, silence 22:00–7:00, nudge only if no mission today and at most once a day; `ReminderNudge` (MobileLayout) shows it in-app with "Hoy no" and "Apagar", a system Notification is used only while the app is open in background, and Perfil offers a daily calendar event (.ics) for reminders with the app closed — why: gentle, easy-to-turn-off reminders that never interrupt the night, without push servers.
